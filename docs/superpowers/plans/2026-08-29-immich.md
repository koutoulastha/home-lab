# Immich Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy Immich to the cluster via ArgoCD, backed by a CloudNativePG Postgres with VectorChord, a 500Gi iSCSI library volume, and reachable both on the LAN and publicly through the Pangolin tunnel.

**Architecture:** Three ArgoCD Applications split by lifecycle — the CNPG operator (`infrastructure/database/cloudnative-pg`), the Postgres `Cluster` and its backup schedule (`apps/immich/db`, never pruned), and the Immich Helm release with its PVC and HTTPRoute (`apps/immich`). Tasks 1–4 author and merge YAML; nothing reaches the cluster until an `application.yaml` is registered by hand, so Tasks 5–8 roll out and verify one Application at a time.

**Tech Stack:** Kubernetes on Talos, ArgoCD, Helm (rendered by ArgoCD, not locally), CloudNativePG 1.30, Postgres 17 + VectorChord, Gateway API (Traefik), democratic-csi on TrueNAS SCALE.

**Spec:** `docs/superpowers/specs/2026-08-29-immich-design.md`

## Global Constraints

- **`main` is the deployment branch.** ArgoCD tracks `targetRevision: main`. Author on a feature branch; merge via PR.
- **No app-of-apps.** Every `application.yaml` must be `kubectl apply`'d once by hand or it deploys nothing. This plan adds three.
- **No plaintext secrets in git.** This feature needs no new secret — CNPG generates `immich-db-app` in-cluster.
- **The user runs all cluster commands.** `kubectl` and `helm` are not installed in this workspace; only `yq` is. Every cluster step in this plan is a copy-pasteable block for the user, and the task waits on their reported output.
- **Repo URL:** `https://github.com/koutoulastha/home-lab.git`
- **Chart versions, pinned exactly:** `cloudnative-pg` **0.29.0** (operator v1.30.0), `immich` **0.12.0**.
- **Image tags, pinned exactly:**
  - `ghcr.io/tensorchord/cloudnative-vectorchord:17.9-1.1.0`
  - Immich server and machine-learning: `v3.1.0` (both, always identical)
  - `docker.io/alpine/kubectl:1.36.4`
- **Storage classes:** `truenas-iscsi` (RWO, default, expandable). `VolumeSnapshotClass` is also `truenas-iscsi`.
- **Gateway:** `traefik-gateway` in namespace `default`. Hostname `photos.koutoulastha.dev`, covered by the existing wildcard cert — **create no Certificate resource.**
- **CNPG cron is six fields, seconds first.** `"0 30 2 * * *"` is 02:30 daily.
- **Immich service/port:** `immich-server:2283`, fixed by the chart.

- [ ] **Step 2: Write `apps/immich/db/cluster.yaml`**

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: immich-db
  namespace: immich
spec:
  instances: 1

  # Tags are <postgres-minor>-<vectorchord-version>; there is no bare `17-x`.
  # Immich v3.1.0 accepts VectorChord '>=0.3 <2' (server/src/constants.ts).
  imageName: ghcr.io/tensorchord/cloudnative-vectorchord:17.9-1.1.0

  postgresql:
    # Without this the vchord extension cannot load and the instance never
    # finishes starting.
    shared_preload_libraries:
      - vchord.so
    parameters:
      shared_buffers: 512MB
      max_wal_size: 2GB
      wal_compression: "on"

  bootstrap:
    initdb:
      database: immich
      owner: immich
      # Immich creates and upgrades its own extensions at boot and needs
      # superuser to do it. Runs against the `postgres` database.
      postInitSQL:
        - ALTER ROLE immich WITH SUPERUSER;
      # Runs against the `immich` database. Pre-creating covers first boot;
      # the superuser grant above covers later version bumps.
      postInitApplicationSQL:
        - CREATE EXTENSION IF NOT EXISTS vchord CASCADE;
        - CREATE EXTENSION IF NOT EXISTS earthdistance CASCADE;

  storage:
    size: 20Gi
    storageClass: truenas-iscsi

  # A separate WAL volume keeps WAL churn during the initial library scan from
  # filling PGDATA, and makes the snapshot backups below self-consistent:
  # CNPG snapshots storage and walStorage together.
  walStorage:
    size: 8Gi
    storageClass: truenas-iscsi

  backup:
    volumeSnapshot:
      className: truenas-iscsi
      # Defaults to `none`, which leaves VolumeSnapshots behind when their
      # Backup is deleted — the prune CronJob would free nothing.
      snapshotOwnerReference: backup
      online: true
      onlineConfiguration:
        immediateCheckpoint: true
        # Defaults to true, which waits for a WAL archiver to process the last
        # segment. There is no WAL archive here, so every backup would hang.
        # The alternative (online: false) fences the primary — on a
        # single-instance cluster that is nightly downtime.
        waitForArchive: false

  resources:
    requests:
      cpu: 200m
      memory: 1Gi
    limits:
      memory: 2Gi
```

- [ ] **Step 4: Write `apps/immich/db/backup-prune-cronjob.yaml`**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: immich-db-backup-prune
  namespace: immich
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: immich-db-backup-prune
  namespace: immich
rules:
  - apiGroups: ["postgresql.cnpg.io"]
    resources: ["backups"]
    verbs: ["get", "list", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: immich-db-backup-prune
  namespace: immich
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: immich-db-backup-prune
subjects:
  - kind: ServiceAccount
    name: immich-db-backup-prune
    namespace: immich
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: immich-db-backup-prune
  namespace: immich
spec:
  # Standard five-field cron — this is a Kubernetes CronJob, not a CNPG
  # ScheduledBackup. 03:30 daily, an hour after the backup runs.
  schedule: "30 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          serviceAccountName: immich-db-backup-prune
          securityContext:
            runAsNonRoot: true
            runAsUser: 65534
            seccompProfile:
              type: RuntimeDefault
          containers:
            - name: prune
              # NOT registry.k8s.io/kubectl — that image is distroless and has
              # no shell, so this script could not run in it.
              image: docker.io/alpine/kubectl:1.36.4
              securityContext:
                allowPrivilegeEscalation: false
                capabilities:
                  drop: ["ALL"]
              command:
                - /bin/sh
                - -c
                - |
                  set -eu
                  KEEP=7
                  NS=immich
                  ALL=$(kubectl -n "$NS" get backups.postgresql.cnpg.io \
                          --sort-by=.metadata.creationTimestamp -o name)
                  TOTAL=$(printf '%s\n' "$ALL" | grep -c . || true)
                  if [ "$TOTAL" -le "$KEEP" ]; then
                    echo "keeping all $TOTAL backup(s), limit is $KEEP"
                    exit 0
                  fi
                  DELETE=$((TOTAL - KEEP))
                  echo "$TOTAL backup(s) present, deleting oldest $DELETE"
                  printf '%s\n' "$ALL" | head -n "$DELETE" | while read -r b; do
                    echo "deleting $b"
                    kubectl -n "$NS" delete "$b"
                  done
              resources:
                requests:
                  cpu: 10m
                  memory: 32Mi
                limits:
                  memory: 64Mi
```

- [ ] **Step 6: Write `apps/immich/db/README.md`**

````markdown
# Immich database

CloudNativePG `Cluster` backing Immich. Separate from `apps/immich` on purpose:
this Application syncs with `prune: false`, so an error in the app's manifests
can never delete the database.

## What is backed up, and what is not

`ScheduledBackup` takes a CSI volume snapshot of the Postgres data and WAL
volumes at 02:30 daily; `immich-db-backup-prune` deletes all but the newest 7 at
03:30. That covers **metadata only** — albums, faces, sharing, admin settings.

**The photos themselves are not covered by anything in this directory.** They
live on the `immich-library` PVC and need a **TrueNAS-side ZFS snapshot task on
the iSCSI parent dataset**, created in the TrueNAS UI. The dataset path is not
in git; read `datasetParentName` from the decrypted driver config:

```bash
kubectl -n democratic-csi get secret truenas-iscsi-driver-config \
  -o jsonpath='{.data.driver-config-file\.yaml}' | base64 -d | grep datasetParentName
```

or read it off the TrueNAS UI. Without that task there is no photo backup.

## Retention depends on a chain that defaults the wrong way

Deleting a `Backup` only reclaims space if every link holds:

1. `Cluster.spec.backup.volumeSnapshot.snapshotOwnerReference: backup` — set
   here. The default is `none`, which orphans VolumeSnapshots.
2. The `VolumeSnapshotClass` `deletionPolicy` must be `Delete`, or the ZFS
   snapshot survives:

```bash
kubectl get volumesnapshotclass truenas-iscsi -o jsonpath='{.deletionPolicy}'
```

## Restore

List available backups:

```bash
kubectl -n immich get backups.postgresql.cnpg.io \
  --sort-by=.metadata.creationTimestamp
```

Restoring replaces the cluster: scale Immich down, delete the `Cluster`, and
recreate it with a `bootstrap.recovery.volumeSnapshots` stanza pointing at the
chosen snapshot, then scale Immich back up. There is **no PITR** — recovery
lands on the snapshot, so up to 24h of metadata can be lost.
````

# values.yaml — notably REDIS_HOSTNAME and IMMICH_MACHINE_LEARNING_URL, which
# are already wired correctly and are deliberately not repeated. The chart's

  main:
    containers:
      main:
        image:

      # domain. Pre-empting it; this cluster has a history of DNS pain.
      - name: ndots
        value: "1"

immich:

    library:
      existingClaim: immich-library
  # Left empty on purpose. Setting it mounts an immich-config.yaml via
  # IMMICH_CONFIG_FILE, which makes every admin setting in the web UI
  # read-only. Settings live in Postgres instead, covered by the DB snapshots.
  configuration: {}

valkey:
  # Chart default is false, while the chart's default REDIS_HOSTNAME already
  # points at <release>-valkey. The one place where its default value and its
  # default wiring disagree.
  enabled: true

server:
  controllers:
    main:
      # The chart hardcodes RollingUpdate. Against an RWO iSCSI library volume
      # that deadlocks every upgrade: the new pod cannot attach a volume the
      # old pod still holds, and the old pod will not terminate until the new

            requests:
              cpu: 500m
              memory: 2Gi

              memory: 2Gi

    cache:
      enabled: true
      # Chart default is emptyDir, which re-downloads ~1-2GB of CLIP and face

      accessMode: ReadWriteOnce
      storageClass: truenas-iscsi
      size: 10Gi

              cpu: 500m
              memory: 1Gi

### Task 6: Deploy the database

**Files:** none unless Step 5 finds a problem.

**Interfaces:**
- Consumes: the CNPG operator (Task 5).
- Produces: Secret `immich-db-app` (key `uri`) consumed by Task 7.

- [ ] **Step 1: Register the Application** *(user runs)*

```bash
kubectl apply -f apps/immich/db/application.yaml
```

Expected: `application.argoproj.io/immich-db created`

- [ ] **Step 2: Wait for the cluster to come up** *(user runs)*

```bash
kubectl -n immich get cluster immich-db -w
```

Expected, after a few minutes: `INSTANCES: 1`, `READY: 1`,
`STATUS: Cluster in healthy state`. Ctrl-C when it settles.

If it sticks on `Setting up primary`, get the reason:

```bash
kubectl -n immich logs immich-db-1 --tail=50
```

A failure naming `vchord.so` means the image tag or
`shared_preload_libraries` is wrong. A failure naming a PVC means the storage
class did not provision — check `kubectl -n immich get pvc`.

- [ ] **Step 3: Confirm the credential Secret exists** *(user runs)*

```bash
kubectl -n immich get secret immich-db-app -o jsonpath='{.data.uri}' | base64 -d | sed 's|://[^@]*@|://***@|'
```

Expected: a `postgresql://***@immich-db-rw.immich:5432/immich` style string.
The `sed` masks the password so it is safe to paste back.

- [ ] **Step 4: Verify the extensions — this is the spec's open item** *(user runs)*

```bash
kubectl -n immich exec -it immich-db-1 -- psql -U postgres -d immich \
  -c "SELECT extname, extversion FROM pg_extension ORDER BY extname;"
```

Expected: rows including `vchord` (version `1.1.0`), `vector`, `cube`,
`earthdistance`, `plpgsql`.

If `vchord` is missing and the error mentioned `vector`, the `CASCADE` did not
resolve pgvector. Fix by adding one line to `apps/immich/db/cluster.yaml`:

```yaml
      postInitApplicationSQL:
        - CREATE EXTENSION IF NOT EXISTS vector;
        - CREATE EXTENSION IF NOT EXISTS vchord CASCADE;
        - CREATE EXTENSION IF NOT EXISTS earthdistance CASCADE;
```

`postInitApplicationSQL` only runs at bootstrap, so a fix here means deleting
and recreating the Cluster — acceptable, it holds no data yet:

```bash
kubectl -n immich delete cluster immich-db
# commit the fix to main, then ArgoCD recreates it
```

- [ ] **Step 5: Confirm the app role has superuser** *(user runs)*

```bash
kubectl -n immich exec -it immich-db-1 -- psql -U postgres \
  -c "SELECT rolname, rolsuper FROM pg_roles WHERE rolname = 'immich';"
```

Expected: `immich | t`

- [ ] **Step 6: Take one backup by hand, rather than waiting for 02:30** *(user runs)*

```bash
kubectl -n immich create -f - <<'EOF'
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  generateName: immich-db-manual-
  namespace: immich
spec:
  method: volumeSnapshot
  cluster:
    name: immich-db
EOF

kubectl -n immich get backups.postgresql.cnpg.io -w
```

Expected: phase reaches `completed` within a couple of minutes. Then:

```bash
kubectl -n immich get volumesnapshot
```

Expected: two snapshots (PGDATA and WAL), `READYTOUSE: true`.

If the Backup hangs in `running`, `waitForArchive` is not `false` — that is the
failure this plan's Cluster config exists to prevent, so re-check
`kubectl -n immich get cluster immich-db -o yaml | grep -A6 volumeSnapshot`.

### Task 7: Deploy Immich

**Files:** none unless a step finds a problem.

**Interfaces:**
- Consumes: Secret `immich-db-app` (Task 6).
- Produces: a running `immich-server` reachable in-cluster on 2283.

- [ ] **Step 1: Register the Application** *(user runs)*

```bash
kubectl apply -f apps/immich/application.yaml
```

Expected: `application.argoproj.io/immich created`

- [ ] **Step 2: Confirm the library volume binds** *(user runs)*

```bash
kubectl -n immich get pvc
```

Expected: `immich-library` `Bound`, `500Gi`, class `truenas-iscsi`; plus a
bound 10Gi ML cache claim.

If `immich-library` stays `Pending`:

```bash
kubectl -n immich describe pvc immich-library | tail -20
```

democratic-csi reports insufficient space on the TrueNAS parent dataset here.
The remedy is either freeing space or lowering the request in
`apps/immich/pvc.yaml` — it can be raised later, the class is expandable.

- [ ] **Step 3: Wait for the pods** *(user runs)*

```bash
kubectl -n immich rollout status deploy/immich-server --timeout=10m
kubectl -n immich rollout status deploy/immich-machine-learning --timeout=10m
kubectl -n immich get pods
```

Expected: `immich-server`, `immich-machine-learning`, and `immich-valkey` all
`Running` and ready.

The machine-learning pod is slow on first start — it downloads models into the
cache volume. That happens once now, not on every restart.

- [ ] **Step 4: If the server crashloops, read the reason** *(user runs)*

```bash
kubectl -n immich logs deploy/immich-server --tail=60
```

- `extension "vchord" is not available` → Task 6 Step 4 did not actually
  succeed; go back and fix the Cluster.
- A DNS failure resolving `immich-db-rw` → confirm the ndots option landed:
  `kubectl -n immich get deploy immich-server -o jsonpath='{.spec.template.spec.dnsConfig}'`
  should print `{"options":[{"name":"ndots","value":"1"}]}`.
- `DB_URL` unset → the Secret name in `apps/immich/values.yaml` does not match
  what CNPG created.

- [ ] **Step 5: Verify the strategy override actually applied** *(user runs)*

```bash
kubectl -n immich get deploy immich-server -o jsonpath='{.spec.strategy.type}{"\n"}'
kubectl -n immich get deploy immich-machine-learning -o jsonpath='{.spec.strategy.type}{"\n"}'
```

Expected: `Recreate` for both.

If either prints `RollingUpdate`, the value is nested wrong in
`apps/immich/values.yaml` — it belongs under `server.controllers.main.strategy`
and `machine-learning.controllers.main.strategy` respectively. Upgrades will
deadlock until this is right, so fix it before continuing.

- [ ] **Step 6: Reach the API without any ingress in the path** *(user runs)*

```bash
kubectl -n immich port-forward svc/immich-server 2283:2283 &
sleep 3
curl -s http://localhost:2283/api/server/ping
kill %1
```

Expected: `{"res":"pong"}`

- [ ] **Step 7: Smoke-test the prune CronJob before its first live run** *(user runs)*

```bash
kubectl -n immich create job --from=cronjob/immich-db-backup-prune prune-smoke-test
kubectl -n immich logs job/prune-smoke-test
```

Expected: `keeping all N backup(s), limit is 7`.

A `Forbidden` error here means the Role's verbs and the script's `kubectl`
flags have drifted apart — check `apps/immich/db/backup-prune-cronjob.yaml`.
Nothing else proves the prune job's RBAC and image work before someone is
watching for it tomorrow at 03:30.

### Task 8: Exposure and hardening

**Files:** none — cluster, Pangolin UI, TrueNAS UI, and Immich UI.

**Interfaces:**
- Consumes: a healthy `immich-server` (Task 7).
- Produces: Immich reachable on the LAN and publicly, with backups actually covering the photos.

- [ ] **Step 1: Confirm the HTTPRoute attached** *(user runs)*

```bash
kubectl -n immich get httproute immich -o jsonpath='{.status.parents[0].conditions}' | yq -P
```

Expected: `Accepted: True` and `ResolvedRefs: True`.

`ResolvedRefs: False` means the backend name or port is wrong — it must be
`immich-server` / `2283`.

- [ ] **Step 2: Test from the LAN** *(user runs)*

```bash
curl -sI https://photos.koutoulastha.dev/api/server/ping
```

Expected: `HTTP/2 200`.

If DNS fails, remember the standing gotcha: `*.koutoulastha.dev` resolves only
via local DNS, and browser DoH breaks it while `curl` works. Test with `curl`
first, and if the browser disagrees with `curl`, it is DoH, not the cluster.

**Do not add a body-size middleware if a large upload later fails.** Traefik
imposes no request-body limit by default — unlike an nginx ingress there is no
1MB cliff to raise — and the mobile app chunks uploads anyway. A failed upload
here is a symptom of something else; adding a middleware will hide it.

- [ ] **Step 3: Create the admin account before anything is public** *(user runs)*

Open `https://photos.koutoulastha.dev` on the LAN. The first visitor becomes
admin — do this now, while the only route in is the LAN one.

Set a strong password. Then in **Administration → Settings**, disable public
registration once your accounts exist.

- [ ] **Step 4: Add the Pangolin resource** *(user, in the Pangolin UI on the VPS)*

- Resource hostname: `photos.koutoulastha.dev`
- Target: `immich-server.immich.svc.cluster.local:2283`
- **SSO / auth: off.** The Immich mobile app cannot traverse an auth portal;
  enabling it here breaks phone backup entirely. Immich's own login is the auth
  boundary, which is why Step 3 comes first.

- [ ] **Step 5: Test from outside the LAN** *(user runs, from a phone on mobile data or any off-LAN host)*

```bash
curl -sI https://photos.koutoulastha.dev/api/server/ping
```

Expected: `HTTP/2 200`.

A `502` means the Newt tunnel is down, not that Immich is broken — check UDP
51820 is open and the newt pod is running:
`kubectl -n pangolin get pods`.

- [ ] **Step 6: Create the TrueNAS ZFS snapshot task — the photos have no backup until this exists** *(user, in the TrueNAS UI)*

Find the dataset the iSCSI volumes live under:

```bash
kubectl -n immich get pv \
  -o custom-columns=NAME:.metadata.name,CLAIM:.spec.claimRef.name,HANDLE:.spec.csi.volumeHandle \
  | grep immich-library
```

Then in TrueNAS: **Data Protection → Periodic Snapshot Tasks → Add**, pointing
at the parent dataset of that volume, recursive, on whatever schedule and
retention you want. Daily with 14 days of retention is a reasonable start.

Nothing in Kubernetes covers the photo library. This step is the backup.

- [ ] **Step 7: Set up the mobile app** *(user)*

Install Immich on the phone, point it at `https://photos.koutoulastha.dev`, log
in, and enable background backup.

Confirm the first upload actually reached the library volume, not just the UI:

```bash
kubectl -n immich exec deploy/immich-server -- df -h /usr/src/app/upload
```

Expected: non-zero `Used` on the 500Gi filesystem, growing as the phone
uploads. If the mount path differs on your image, find it with
`kubectl -n immich get deploy immich-server -o jsonpath='{.spec.template.spec.containers[0].volumeMounts}'`.

- [ ] **Step 8: Confirm the nightly schedule fires** *(user runs, the day after)*

```bash
kubectl -n immich get backups.postgresql.cnpg.io --sort-by=.metadata.creationTimestamp
kubectl -n immich get cronjob immich-db-backup-prune
```

Expected: a `completed` backup dated 02:30, and the CronJob showing a recent
`LAST SCHEDULE`. The prune will report `keeping all N backup(s), limit is 7`
until there are more than seven — check its output with:

```bash
kubectl -n immich logs job/$(kubectl -n immich get jobs -o name | grep backup-prune | tail -1 | cut -d/ -f2)
```
